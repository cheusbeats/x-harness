# 04 — Субагенты, делегирование, MCP и внешние роли

**Что это:** карта делегирования — восемь проектных субагентов, правила оркестрации, ступень local-workers, MCP-инструменты и роли, которые живут вне git.
**Когда читать:** когда планируешь передать работу субагенту, пишешь его brief, принимаешь результат или переносишь обвязку на другого агента.
**Срез:** 30.10.2026. Источники — `.claude/agents/*.md`, `CLAUDE.md` (§ Orchestration workflow), `.claude/reference/local-workers.md`, `outputs/AGENT_HARNESS.md`.

## 1. Где живут роли и что в них записано

- Проектные роли — восемь Markdown-файлов в `.claude/agents/`; имя файла совпадает с `name` во frontmatter. Больше проектных ролей в репозитории нет.
- Frontmatter каждого файла содержит `name`, `description`, `model`, `color`. Поля `tools` (allowlist инструментов) нет ни в одном файле: границы роли записаны текстом («Do NOT implement», «report, not fix», «Touch only the files named»), а фактический доступ к инструментам определяется средой и её разрешениями.
- Описание роли — это триггер для оркестратора: `description` начинается с «Use for…»/«Use when…» и перечисляет задачи, для которых роль создана.
- Перенос: для Claude Code — файл по пути `.claude/agents/<name>.md` с тем же frontmatter. Для другого клиента содержимое переносится в его штатный механизм ролей; наличие файлов само по себе не подключает роли в произвольном агенте.

## 2. Восемь проектных субагентов

| Роль | Модель | Когда звать | Что обязан сделать | Чего не делать |
|---|---|---|---|---|
| `deep-reasoner` | `fable`; если недоступна — respawn с override `opus` | архитектура, сложный debugging, алгоритмы, review плана, trade-off | прочитать код/план, дать ровно одну рекомендацию с обоснованием, evidence с `file:line`, формат **Conclusion / Evidence / Recommended actions**; для «для каждого X» сначала перечислить множество программно | не реализовывать, не редактировать файлы, не запускать write-команды; deliverable — только вывод |
| `ui-builder` | `sonnet` | Livewire-страница, Blade-view, x-component, таблица, drawer, modal, chart, empty state | до кода: `laravel-best-practices` + Boost `search-docs`; открыть ближайшую существующую страницу и повторить её; финиш — Pint → узкие тесты → Dusk; отчёт с соблюдёнными секциями | не изобретать layout/шкалу отступов/цвета; не писать `@php`; не использовать `wire:confirm`/`alert`/`prompt`; не запускать npm через sail |
| `db-surgeon` | `sonnet` | миграции, индексы, схема, медленный/N+1/per-row запрос, аудит hot path | смотреть реальную схему (`database-schema`, `database-query`); выбрать низшую ступень лестницы Eloquent → Query Builder → raw SQL; raw — с коротким комментарием, чего не умеет билдер; реверсивный `down()`; индекс в той же правке | не делать `migrate:fresh`/`db:wipe`; не выполнять деструктивную миграцию на заполненной таблице без явного согласия |
| `test-writer` | `sonnet` | PHPUnit Feature/Unit, Dusk, тесты полноты «для каждого X» | до тестов: `laravel-best-practices` + `search-docs` по testing API; только PHPUnit (Pest конвертировать); `make:test --phpunit`; фабрики и существующие states; happy/failure/edge; enumeration-тест по образцу `test_every_issue_type_has_instruction_file`; Dusk для интерактивного UI в темпе Feature-теста | не удалять и не ослаблять существующие тесты ради зелёного прогона; не чистить БД, кроме собственной Dusk-БД |
| `plan-keeper` | `sonnet` | `planning/`: drift-находки, строки реестров, HF-записи, закрытие плана | работать только через `registry.sh`; читать строку индекса и `## Резюме`, а не тело плана; для drift источник истины — `git log` и код; закрытые записи не переписывать | не править индексы Edit/Write; не закрывать план без явного слова владельца и маркера `owner-ok`; не запускать `owner-ok.sh` и не писать `.claude/state/owner-ok` |
| `compliance-checker` | `sonnet` | перед выпуском фичи, работающей с данными пользователей/посетителей; аудит зависимостей; секреты в diff | ответить на пять вопросов 152-ФЗ; `composer audit` в контейнере и `npm audit` на хосте; скан diff на секреты; auth/authz, `authorize()` в FormRequest, mass assignment; outbound-вызовы с данными клиента | только отчёт; не исправлять; не смягчать `blocker` до `note`; не выдумывать риски «для полноты» |
| `implementer` | `sonnet` | реализация уже принятого решения, не попавшая в домены выше | следовать принятому подходу; `laravel-best-practices` + `search-docs`; сверить соседний файл; Pint → узкие тесты; отчёт | не перепроектировать подход — если он не работает, остановиться и вернуть блокер; не трогать файлы вне задания |
| `fast-worker` | `haiku`; `sonnet` при нечётком ТЗ или нужде в суждении | механические задачи с точным spec: переименования, boilerplate по шаблону, форматирование, описанная правка по списку файлов, прогон команд | исполнять ровно spec; трогать только названные файлы; сверить один sibling-файл; PHP/artisan/composer — через sail, npm — на хосте; Pint после PHP | не принимать design-решений, не расширять scope, не «улучшать» попутно; при двусмысленности — STOP и открытый вопрос |

Полные тексты ролей (для точного воспроизведения файлов) — `outputs/AGENT_HARNESS.md`, § «Полные определения проектных субагентов». Тексты содержат устаревшее упоминание PHP 8.4 (фактически проект требует `php ^8.5.12`, см. `references/06-environment.md`) и последовательность «Pint → test», которая не отменяет общего правила «Larastan перед каждым тестом» (ниже, § 6).

## 3. Карта делегирования из CLAUDE.md

Оркестратор — модель `opus` (`.claude/settings.json` → `"model"`). Он планирует, декомпозирует и синтезирует; сам пишет только тривиальные однострочные правки. Таблица ниже — дословная карта; **побеждает первая совпавшая строка**.

| Задача | Агент | Модель |
|---|---|---|
| Архитектура, сложный debugging, алгоритмы, review плана | `deep-reasoner` | fable; при недоступности — respawn с override `opus` |
| **UI**: Livewire-страница, Blade-view, компонент, таблица, drawer, chart | `ui-builder` | sonnet |
| **DB**: миграции, индексы, медленные/N+1/per-row запросы | `db-surgeon` | sonnet |
| **Тесты**: PHPUnit, Dusk, enumeration-тесты «для каждого X» | `test-writer` | sonnet |
| **planning/**: drift, строки реестров (`registry.sh`), HF-записи, закрытие плана | `plan-keeper` | sonnet |
| **Аудит перед выпуском**: 152-ФЗ, `composer`/`npm audit`, секреты в diff | `compliance-checker` | sonnet |
| Реализация принятой фичи/фикса, не попавшая ни в один домен | `implementer` | sonnet |
| Механическая работа с точным spec: переименования, boilerplate, форматирование, команды | `fast-worker` | haiku; spawn с override `sonnet`, если spec нечёткий |
| Найти код («где X», «кто вызывает Y», карта каталога) | `cavecrew-investigator` / `Explore` | — |
| Ревью diff/ветки | `cavecrew-reviewer` или `/code-review` | — |
| Свежий взгляд, второе мнение, тупик | Codex (`/codex:rescue --background`) | GPT — пэр `deep-reasoner`, не ревьюер |

Смысл доменных ролей — держать большие документы вне контекста оркестратора: `ui-builder` загружает UI-навыки в своём окне, `plan-keeper` работает через `registry.sh` и резюме планов. Поэтому делегируется **целый слой**, а не фрагмент: субагент, вернувший вопрос, означает, что spec был тонким; субагент ради двухстрочной правки стоит дороже, чем экономит.

Последние три строки таблицы (поиск, ревью, Codex) **не определены** в восьми проектных файлах — это внешние зависимости (плагины, встроенный Explore). Если в целевом агенте их нет, делегирование по этим строкам просто не существует; заменять их «похожими» ролями нельзя.

## 4. Правила оркестрации

- **Параллельность.** Независимые подзадачи запускаются в одном сообщении; последовательно — только реальные зависимости.
- **Полная спека делегации.** Каждая делегация несёт: цель, точные пути файлов, критерии приёмки и что НЕ трогать. Обязательные навыки и запреты роли в brief не пересказываются — они уже в определении роли.
- **Вопрос от субагента — дефект спеки.** Исправлять spec и переотправлять, а не слепо повышать модель.
- **Проверка результата.** Отчёт субагента — утверждение, не результат. Перед приёмкой: `git status`/diff, отсутствие лишних правок, критерии приёмки, целевые тесты, при необходимости статические проверки; затем `.claude/scripts/quality-gate.sh` (Larastan → Pint → PHPUnit → eslint). Провал — переотправка с выводом гейта в качестве spec.
- **Высокая цена ошибки.** `deep-reasoner` и Codex запускаются параллельно на одну задачу; синтез — лучший вариант, при этом ни одному не показывают ответ другого.
- **Контекст.** Оркестратор не читает тела планов и большие справочники, если это может сделать доменная роль. Субагент возвращает выводы, а не транскрипт.

### 4.1 Формат отчёта, который роль обязана вернуть

Отчёт — часть контракта роли: по нему оркестратор принимает работу, не читая транскрипт.

| Роль | Что вернуть |
|---|---|
| `deep-reasoner` | **Conclusion** 1–3 предложения; **Evidence** с `file:line`; **Recommended actions** нумерованными шагами, готовыми для `implementer`/`fast-worker` без переписывания |
| `ui-builder` | изменённые файлы (`file:line`), какие секции навыка соблюдены, команда теста и дословная строка результата, что осознанно отложено; содержимое навыка обратно не вставлять |
| `db-surgeon` | изменения схемы/запроса (`file:line`), выбранная ступень лестницы и почему выше Eloquent, индекс добавлен или подтверждён, before/after по количеству запросов или времени на hot path |
| `test-writer` | добавленные тестовые файлы (`file:line`), что именно каждый фиксирует, точная команда и дословная строка результата, непокрытое поведение и причина |
| `plan-keeper` | какие строки/файлы изменены (точные строки) и какая несогласованность осталась нетронутой; без пересказа содержимого планов |
| `compliance-checker` | одна строка на находку: `severity \| file:line \| что не так \| что исправит`, где severity — `blocker` / `risk` / `note`; явно сказать, если категория чиста |
| `implementer` | файлы (`file:line`), команда теста и дословный результат, что сознательно пропущено или упрощено; без прозы |
| `fast-worker` | изменённые файлы (`file:line`), выполненные команды, дословные строки pass/fail; без прозы |

### 4.2 Пример brief'а (делегирование целого слоя)

```text
Роль: ui-builder
Цель: страница /projects/{project}/scans — список сканов с сортировкой и пагинацией.
Файлы: app/Livewire/... (новый), resources/views/livewire/... (новый), routes/web.php (строка маршрута).
Данные: коллекция Scan (id, started_at, status, pages_count, error_count), уже загруженная компонентом.
Критерии приёмки: список повторяет существующую list-страницу; сортируемые th; x-pagination + WithListPagination;
пустое состояние как на соседних страницах; Dusk-тест открывает drawer.
НЕ трогать: миграции, модели, queue-конфиг; не менять чужие Blade-компоненты.
```

Тот же каркас работает для любой роли: меняются обязательные поля (схема/миграции для `db-surgeon`, набор поведений для `test-writer`, «уже принятый подход» для `implementer`, точный diff для `fast-worker`).

### 4.3 Доменные границы

- `deep-reasoner` работает **до** решения; `implementer`/`fast-worker` — **после** него. Передавать `implementer` открытый вопрос «как лучше» запрещено — сначала `deep-reasoner`.
- `ui-builder` владеет Blade/Livewire-слоем, `db-surgeon` — схемой и запросами. Пересечение (UI, тянущий N+1) решается как два последовательных слоя: сначала запрос, потом представление.
- `test-writer` пишет тесты к уже сданному поведению либо к фиксу; он не проектирует поведение и не исправляет прод-код, кроме минимальной причины падения теста по правилу из § 7.
- `plan-keeper` не решает, что делать, — он приводит реестры в соответствие с кодом и git.
- `compliance-checker` не блокирует мерж сам: он отдаёт findings, решение и исправление — за оркестратором.

## 5. Модели ролей: что переносимо

| В исходной обвязке | Смысл | При переносе |
|---|---|---|
| `fable` | максимальная глубина рассуждения | подставить самую сильную доступную reasoning-модель |
| `opus` | оркестратор; fallback для `deep-reasoner` | сохранить роль «сильная модель верхнего уровня» |
| `sonnet` | рабочие доменные роли | средняя модель с достаточным контекстом |
| `haiku` | дешёвый механический исполнитель | самая дешёвая быстрая модель; при нечётком spec — модель выше |

Имена `fable/opus/sonnet/haiku` — псевдонимы Claude, не переносимый API. Переносится назначение роли, глубина рассуждения и независимость ревью, не имя. Независимого ревьюера нельзя имитировать «второй подписью» того же агента.

## 6. Оркестрация и проверки: требуется vs фактически

| Утверждение | Где заявлено | Как обстоит фактически |
|---|---|---|
| Оркестратор пишет только однострочные правки | `CLAUDE.md` § Orchestration workflow | правило процесса: хука, который это проверяет, нет — дисциплина агента |
| Результат субагента принимается только после гейта | `CLAUDE.md`; `.ai/guidelines/environment.md` | `.claude/hooks/commit-gate.sh` запускает `quality-gate.sh --fast` перед `git commit`; отдельного события «приёмка субагента» нет — оркестратор обязан прогнать гейт сам |
| `deep-reasoner` не редактирует файлы | текст роли | allowlist `tools` в файле отсутствует; фактический запрет обеспечивается только инструкцией и правами среды |
| Роли используют модели fable/opus/sonnet/haiku | frontmatter | в текущем окружении `fable` может быть недоступна — тогда override `opus` |
| PHP 8.4 в текстах `deep-reasoner`/`implementer` | `.claude/agents/*.md` | `composer.json` требует `php ^8.5.12`; CI падает на PHP < 8.5.12 |
| «Pint, затем узкие тесты» в ролях | `.claude/agents/*.md` | общее правило сильнее: перед каждым тестом — Larastan (`CLAUDE.md` § Git workflow) |
| Независимое ревью двух моделей на деньгах | `CLAUDE.md`, личная память | правило процесса и личное соглашение; механического enforcement нет |

## 7. `local-workers` — ступень ниже субагента

Источник: `.claude/reference/local-workers.md`. Действует, **только если в сессии реально доступен MCP-сервер `local-workers`**; иначе этой ступени не существует и упоминать её не нужно.

- **Имена работников не зашиты** — состав меняется, поэтому маршрутизация по роли, а не по имени: выбирается самый лёгкий worker, подходящий задаче. Более тяжёлый — не fallback для рутины; если задача велика для лёгкого, её сначала дробят.
- **Думает всегда оркестратор:** понимает запрос, читает архитектуру, принимает подход, очерчивает границу, декомпозирует, проверяет diff. Worker никогда не получает исходный пользовательский запрос — только подготовленную самодостаточную подзадачу.
- **Eligible:** одна цель, 1–3 файла, архитектура уже решена, конкретный ожидаемый результат, целевая команда проверки, один независимый запуск. Примеры: локальный багфикс; метод/класс по готовому контракту; правка одного service/repository/action/job; правило валидации; enum/mapping/DTO/value object; подключение готового механизма в одно место; unit/feature/regression тесты; мелкая CRUD/API/UI-правка при решённой архитектуре; механическая правка по явному списку мест.
- **Never eligible:** проектирование архитектуры и выбор подхода, понимание всего проекта, репозиторный/кросс-каттинг рефакторинг, product-решения, неясные требования, backward compatibility, infra/deploy без точного плана, массовые schema-изменения, работа по десяткам файлов без присмотра, «изучи проект и сделай X», «разберись, почему сломано» без локализации.
- **Контекст worker'а минимален и свеж на каждый вызов:** цель, факты, которые нельзя угадывать, точные пути, ожидаемое поведение, границы scope, команда проверки. Никогда: вся беседа, история проекта, `CLAUDE.md`/`AGENTS.md` целиком, «весь репозиторий для контекста». Worker не отправляют читать `CLAUDE.md` — оркестратор сам извлекает нужные ограничения в текст задачи.
- **Один bounded step на вызов**, не несколько независимых просьб. При неясной архитектуре — STOP.
- **Только последовательно.** Два local worker'а параллельно не запускаются; второй не стартует, пока первый полностью не завершился.
- **Failing test:** actual/expected → непосредственный producer → максимум один уровень helper/зависимости → один минимальный фикс → rerun. Не более двух циклов diagnose/fix, затем STOP с конкретным блокером.
- **`STATUS: success` ничего не доказывает.** После каждого вызова оркестратор независимо проверяет `git status`, фактический diff, отсутствие посторонних правок, критерии приёмки, targeted-тесты и статические проверки — та же дисциплина «verify before accepting», что и для любого субагента, через `quality-gate.sh` там, где применимо. Workers не commit/push/merge.

## 8. MCP-инструменты по ролям

Проектный MCP-сервер — Laravel Boost (`.mcp.json`):

```json
{
  "mcpServers": {
    "laravel-boost": {
      "command": "vendor/bin/sail",
      "args": ["artisan", "boost:mcp"]
    }
  }
}
```

Правило №1: **`search-docs` вызывается до любого вызова API Laravel 13 / Livewire 4 / Filament 5** — это не навык, а инструмент, и он обязателен всегда, когда документация доступна. Сервер объявляет инструменты (классы `vendor/laravel/boost/src/Mcp/Tools/`): `search-docs`, `database-schema`, `database-query`, `database-connections`, `get-absolute-url`, `application-info`, `tinker`, `browser-logs`, `last-error`, `read-log-entries`, `record-rule`. Точный список доступного в сессии смотреть у клиента, а не по памяти.

| Роль / фаза | Инструменты | Назначение |
|---|---|---|
| Любая правка кода | `search-docs` | документация под установленные версии пакетов; никогда не писать вызов по памяти |
| `db-surgeon` | `database-schema`, `database-query` | фактическая схема и read-only проверки вместо догадок по моделям и tinker |
| `test-writer` | `search-docs` (testing API), при нужде `tinker` | хелперы Laravel 13 / Livewire 4 / Filament 5 |
| `ui-builder`, `implementer` | `search-docs`; `get-absolute-url` для проверки маршрутов | верные API и URL |
| Отладка | `last-error`, `read-log-entries`, `browser-logs` | свежие ошибки и логи |
| Диагностика проекта | `application-info` | версии и окружение приложения |

MCP `local-workers` регистрируется **вне репозитория** — в `~/.claude.json` через внешний исполняемый файл Workus (`~/Library/Application Support/Workus/bin/workus-mcp`). С git этот runtime не приезжает: на новой машине его либо ставят отдельно, либо ступень § 7 отсутствует.

## 9. Внешние пользовательские роли и личная память (не часть git)

Всё ниже лежит в домашнем каталоге и **не переносится** вместе с репозиторием. Для воспроизведения обвязки это необязательный слой; без него проектные восемь ролей работают, но исчезают персональные привычки владельца.

**Пользовательские агенты `~/.claude/agents/`** — персональный слой вне репозитория; при совпадении имён с проектными порядок разрешения задаёт клиент, поэтому для проекта источником считаются файлы `.claude/agents/`:

|---|---|---|
| `deep-reasoner.md` | `opus` | `memory: user` — постоянная память агента между сессиями |
| `fast-worker.md` | `sonnet` | `memory: user` |
| `impeccable-asset-producer.md` | `inherit` | allowlist `tools: Read, Write, Edit, Bash, Glob, Grep`, `maxTurns: 24` |
| `impeccable-documenter.md` | `inherit` | `tools: Read, Write, Bash, Glob, Grep`, `maxTurns: 30` |
| `impeccable-finish-reviewer.md` | `inherit` | только чтение и команды, `effort: high` |
| `impeccable-manual-edit-applier.md` | `inherit` | `maxTurns: 12`, применяет правки кода |

**Роли из плагинов** (ставятся отдельно, см. `references/05-skills.md`): `cavecrew-investigator`, `cavecrew-builder`, `cavecrew-reviewer` (плагин Caveman), агенты плагина Codex Companion. Встроенный `Explore` — механизм самого клиента, не файл репозитория.

**Личная память:** `~/.claude/projects/<путь проекта>/memory/MEMORY.md` и записи рядом. Git их не переносит; в экспорт включают только актуальные общие ограничения, без истории аккаунта, токенов, credentials и кэшей. Полезные переносимые правила из памяти: `rules-enforced-by-hooks.md` (новое проверяемое правило требует hook + тест hook + adapter, текста в `CLAUDE.md` недостаточно), `plan-review-checklist.md` (десять проверок плана), не создавать ad-hoc Docker preview-контейнеры, при mutation-проверке сохранять файлы копией (`git checkout` не восстанавливает untracked). Память содержит устаревшее: закрытые/открытые статусы планов, старые STATUS/JOURNAL, старый полный запрет агентского merge, старые версии плагинов — как единый нормативный источник её копировать нельзя.

**Переопределение Superpowers:** скиллы Superpowers по умолчанию пишут планы в `docs/superpowers/`; здесь это явно переопределено — дизайн живёт разделом внутри `planning/plans/PLAN-{N}-*.md`.

## 10. Найденные расхождения и пробелы

- **Границы ролей не механизированы.** Ни один файл роли не задаёт `tools`; запреты — только текст. Клиент с широкими правами позволит `deep-reasoner` писать файлы; клиент с узкими — может не дать `ui-builder` нужных инструментов.
- **Приёмка результата не автоматизирована.** Гейт привязан к `git commit`, а не к факту возврата субагента. Правило «результат принимается после гейта» — процесс, а не hook.
- **Внешние строки карты делегирования** (`cavecrew-*`, `Explore`, `/codex:rescue`, `/code-review`) не определены в репозитории; в целевом агенте их нужно либо установить, либо явно объявить отсутствующими.
- **Модели ролей** — псевдонимы Claude; при переносе нужен mapping на доступные модели, иначе роли не создадутся.
- **`local-workers`** существует только при живом MCP-сервере; регистрация сервера лежит вне git.
- **Устаревшие фразы в ролях:** «PHP 8.4» и последовательность «Pint → test». Ссылка на `planning/ACTIVE_PLANS.md` как «срез на сейчас» — актуальна.
